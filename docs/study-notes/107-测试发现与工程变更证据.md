# 测试发现与工程变更证据

## 1. 测试层次与发现边界

Unit test 通常验证一个函数、类或小模块的局部行为；Integration test 验证多个真实组件之间的契约；E2E test 从外部入口验证完整用户流程。三者的执行成本、依赖和失败定位范围不同。

G10-02 的 `find_tests` 只回答“这个源码 path 附近可能有哪些候选测试”，不回答“改动一定影响哪些测试”，也不运行 pytest、Maven、Gradle 或其他测试命令。后一个问题属于 Change Impact 层，而不是 bounded discovery Tool 的职责。

## 2. 目录与命名约定

确定性发现可以先利用项目已经存在的工程约定：

- Python 常见 `test_foo.py` 与 `foo_test.py`。
- Maven/Java 常见 `src/main/...` 与 `src/test/...` 镜像目录，以及 `FooTest.java`、`FooTests.java`。
- JavaScript/TypeScript 常见 `foo.test.js`、`foo.spec.js`、对应的 jsx/tsx 形式。
- Go 常见 `foo_test.go`。
- C# 常见 `FooTest.cs`、`FooTests.cs`。
- 通用 `test`、`tests`、`__tests__` 目录也是候选测试路径信号。

`src/main/java/a/b/Foo.java` 到 `src/test/java/a/b/FooTests.java` 是高置信度的 `mirrored_path`。`runtime.py` 到 `tests/test_tool_agent_runtime.py` 主要依赖 `filename_match`。如果测试文件名没有明显关系，但正文出现 `PaymentService`，则可通过 `content_reference` 作为较弱候选。

## 3. 三种稳定 reason

`find_tests` 只返回三个 reason：

- `mirrored_path`：识别到 `src/main` 到 `src/test` 的镜像位置与测试类名变体。
- `filename_match`：源码 stem 与测试文件名有明显 lexical 关系。
- `content_reference`：候选测试正文中出现源码 stem。

多个 reason 可以同时返回，reason 顺序固定为上面的优先级。候选按最佳 reason 的优先级排序，同等级按 repo-relative POSIX path 排序。最多返回 10 个，`truncated=true` 表示候选被截断。

## 4. Candidate 不等于 Evidence

候选 path 和 anchor line 只是定位事实，不能证明测试一定受改动影响。`find_tests` 不返回测试正文，也不创建 Engineering Evidence。需要可靠回答测试如何验证行为时，调用链应是：

```text
find_tests(path)
    -> candidate path + anchor line
    -> read_project_context(path, line)
    -> project_test evidence
```

读取成功的测试上下文才产生 `project_test`，与 `project_code`、`project_doc`、`project_change` 分开。这样报告可以区分：变更 diff、实现上下文和测试验证上下文，而不是把所有内容都标成普通代码。

## 5. 为什么先用 heuristic

filename、目录镜像和 literal content reference 不需要构建索引，也不依赖语言解析器；同样输入会得到同样排序，结果容易测试、审计和解释。它适合先回答“测试在哪里”，但不能推断 import、调用关系、参数流或运行时覆盖。

因此当前不做 AST、LSP、import graph、call graph、coverage analysis 或 semantic test retrieval。它们会增加语言覆盖、版本、缓存和 provenance 复杂度，应由后续 Change Impact 需求及其评测证据驱动。

## 6. 为什么复用 code_search

当前 `code_search` 已经能在测试目录中做 literal symbol、method、config key 和 exception 搜索：

```text
code_search(symbol)
    -> path + line
    -> read_project_context
```

这已经覆盖 reference locating。新增 `reference_search` 会与 `code_search` 重叠，增加模型选错 Tool 的概率。`find_tests` 的独特职责是从一个 source path 出发，按测试目录和命名约定生成候选集合；它不是第二个通用搜索器。

## 7. 安全与预算

输入必须是 bounded repo-relative path；绝对路径、Windows drive、`..`、控制字符和 secret-like source path 会被拒绝。工具不接受 repo root、cwd、glob 或 regex，不执行 shell、不运行测试、不修改文件。扫描复用现有 allowed suffix、excluded directories、1 MiB file bound、UTF-8 文本读取、secret filtering、symlink rejection 和 containment check。目标 source 即使已删除或不存在也允许查询。

候选输出只有 path、line、reasons、returned_count、truncated 和 omitted_sensitive_count，没有绝对本机路径和文件正文。Runtime 的 5 iterations / 4 tool calls / 2 tool errors 保持不变。一个完整的变更检查可以在五轮内走完：

```text
changed_files -> git_diff -> find_tests -> read_project_context -> final_answer
```

这条链路正好使用 4 次 Tool call、5 次 iteration，并产生 `project_change` 与 `project_test` 两类 evidence。

## 8. 和 Git Change Evidence 的组合

`changed_files` 先定位修改文件，`git_diff` 读取单文件 bounded diff；如果需要知道相关测试在哪里，再把 changed path 传给 `find_tests`。随后只读取选定的测试上下文。这个组合仍然没有宣称测试必然受影响：它把变更、候选和实际读取的测试证据分层保存，为后续 Change Impact 提供可审计输入。

## 9. 后续演进与面试讲法

后续 Change Impact 可以在候选测试之上增加更强的证据，例如 import/call graph、测试执行结果或人工确认，但必须单独定义边界和评测。当前实现可以这样介绍：

“我增加了一个 bounded `find_tests` Tool。它不运行测试，也不假装完成影响分析，而是用测试目录、命名约定、Maven 镜像结构和 literal 内容引用做确定性候选发现。模型拿到候选 path 后，再通过 `read_project_context` 读取真实测试上下文，Runtime 将其标成 `project_test` evidence；预算仍是 5/4/2，Git diff 和测试证据可以在一个四 Tool、五轮链路中同时保留。”
