# 离线消融与正式可复现实验（G2-ABL-16）

> 2026-08-08 — 610 → 624 tests（R1 增加 Runtime Binding 与 Sparse Integrity 契约测试）
> 离线消融负责"快速提出假设"，正式实验负责"给假设一个可审计的
> 身份"。两者不能互相替代，但可以互相验证。

## 1. 什么是消融实验

Ablation study = 从完整系统中隔离某个组件，观察指标变化。

```text
完整系统：Dense + BM25 + RRF
消融 A：只用 Dense
消融 B：只用 BM25
```

为什么一次只改变一个变量：同时改两个变量时，指标变化无法归因；
一次只切换一个组件，才能把差异解释给"这个组件"。

## 2. 什么叫控制变量

控制变量 = 除被测变量外，其余全部保持不变。

本项目：

```text
不变：Corpus / Gold / Query / Chunk 配置 / Embedding 配置 / Top-K /
      索引构建输入与相关配置

隔离：每个 formal experiment 使用自己的 Workspace 和独立索引实例

改变：retriever_strategy（simple / bm25 / hybrid）
```

注意：`dense_candidate_k`、`sparse_candidate_k`、`rrf_k`、
`rrf_tie_breaker` 仍存在于统一 ExperimentConfig，但 simple/bm25
策略实际不消费它们——"字段存在"不等于"策略使用"。

## 3. offline / counterfactual ablation 是什么

offline ablation 复用一次运行中已经保存的中间结果：

```text
canonical Hybrid 运行时已保存：
  Dense Top-30
  Sparse Top-30
  Final Top-5
```

于是可以"离线推导"：如果只用 Dense Top-5，指标是多少？如果只用
Sparse Top-5，指标是多少？不需要再跑任何检索。

## 4. offline ablation 的优点

- 快：不需要重新 Embedding / Search；
- 省：不需要新索引、新实验 Artifact；
- 同源：Query、Chunk、索引、Embedding 完全来自同一次运行，环境
  差异最小；
- 适合提出假设：先看趋势，再决定要不要正式验证。

## 5. offline ablation 的局限

- 没有独立 `experiment_id` / `retrieval_run_id` / `result_id`；
- 排序逻辑在分析脚本里，而不是正式 Retriever 运行时；
- 无法被当作"某个策略的正式实验事实"；
- 如果正式实现与离线假设路径不等价（比如不同 Top-K 语义、不同
  tie-break），离线结论可能失真。

## 6. formal experiment 是什么

```text
ExperimentConfig
→ experiment_id（配置身份的哈希）
→ prepare（独立 Workspace + 派生 config + Pipeline）
→ index_corpus（index_manifest.json）
→ run_retrieval（retrieval_results.json）
→ compute_retrieval_metrics（retrieval_metrics.json）
→ finalize_result（result.json）
```

每一步都有磁盘 Artifact、绑定校验和原子写入，可被独立审计。

## 7. 为什么正式实验需要独立 ID

面试追问："既然离线已经算出结果了，为什么还要再跑？"

回答要点：

1. 离线结果是"推导"，正式结果是"执行"；
2. 策略不同 = 算法行为不同，必须有不同 `experiment_id`，否则两个
   实验无法区分；
3. `experiment_id` 是复现契约：任何人拿到相同配置都能重建；
4. 只有正式 Artifact 才能支撑"该策略在 Benchmark 上表现如何"的
   结论。

## 8. 什么叫 parity validation

Parity = 两个来源的结果是否一致。

为什么不仅看宏指标：宏平均会把逐 Case 差异折叠掉（比如修复 1 个、
丢失 1 个，宏平均可能不变）。

所以还要比较：

```text
50 Case 的逐 Case document ranking 是否 exact match
（可选）Top-5 chunk_id 顺序是否 exact match
```

## 9. 如果 offline 与 formal 不一致意味着什么

不一致不代表"某一个错了"，而是说明实现路径不等价，可能来自：

```text
Top-5 Chunk 语义不同（先取 chunk 还是先取文档）
排序语义差异（RRF tie、BM25 tie、Dense near-tie）
索引差异（重建顺序 / 构建随机性）
nondeterminism（Embedding、HNSW、hash seed）
实验污染（复用旧索引、重复执行）
metadata / document mapping 差异
```

正确动作：定位差异来源，而不是"调参数对齐数字"。

## 10. 用本项目真实结果举例

```text
offline：
Dense Hit0.88 / Recall0.8633 / MRR0.7483 / nDCG0.7624
BM25  Hit0.98 / Recall0.9533 / MRR0.7873 / nDCG0.8206

formal（独立正式实验）：
Dense Hit0.88 / Recall0.8633 / MRR0.7483 / nDCG0.7624
BM25  Hit0.98 / Recall0.9533 / MRR0.7873 / nDCG0.8206

parity：Dense 50/50、BM25 50/50（文档粒度与 chunk 粒度均为 50/50）
```

正式结论（限当前 50 Case / top-5-chunk 语义）：

```text
BM25-only > Hybrid > Dense-only
```

## 11. 面试追问

### Q：什么是 ablation study？

一次只移除/隔离一个组件，观察指标变化，判断每个组件的边际贡献。

### Q：为什么一次只改一个变量？

同时改多个变量会让指标变化无法归因。

### Q：offline ablation 能代替正式实验吗？

不能。它适合提出假设；正式实验才提供可审计的独立身份和 Artifact。

### Q：如何保证 A/B 实验公平？

控制 Corpus、Gold、Query、Embedding 配置、Chunk 配置、Top-K、
索引构建输入与相关配置保持一致；每个 formal experiment 的物理
Workspace / 索引实例独立隔离。只切换被测变量，并确保随机性 /
tie-break 确定。

### Q：宏指标一样是否代表两个实验完全一致？

不代表。可能修复与回归互相抵消；必须比较逐 Case ranking（parity）。

### Q：为什么要比较 Case-level parity？

宏平均会折叠方向性差异；逐 Case 才能发现"某些 Case 变好、某些
变坏"。

### Q：experiment_id 有什么价值？

它是实验身份的稳定哈希：相同配置 → 相同 ID；配置变化 → ID 变化；
让"哪个实验"可被精确引用和复现。

### Q：如果两次结果不一致你怎么排查？

按序检查：Top-K 语义 → 排序/tie-break → 索引构造 → 随机性 →
污染 → metadata/mapping；定位后如实报告，不调参数对齐。

## 12. 为什么 Runtime Retriever Binding 很重要

只验证 YAML / config 文本不够。考虑：

```text
Config 写 bm25
但实际 Retriever 因构造 Bug 变成 SimpleRetriever
```

如果只验证 `pipeline.config.retriever_strategy`：

```text
实验身份会撒谎：declared configuration == bm25
effective runtime behavior == dense-only
```

因此正式实验必须用真实类型判断（`isinstance`）验证：

```text
simple → SimpleRetriever
hybrid → HybridRetriever
bm25   → BM25OnlyRetriever
mmr    → MMRRetriever
```

这是"声明配置"与"实际运行行为"的一致性校验。

## 13. BM25-only 的当前基础设施事实

BM25-only 的 Retrieval ranking 只依赖 BM25，不执行 Dense Search / RRF。

但是当前项目复用统一 Pipeline / index_file：

```text
文档仍会经过 Embedding 并写入 Chroma
```

这是基础设施复用造成的工程成本，**不代表 BM25 排名依赖 Dense**。

通用原则：

```text
组件被构造 / 参数存在
≠
当前 strategy 的排序结果消费它
```

## 14. sparse_index_count 的意义

对 BM25 正式实验：

```text
vector_store_count = 215
```

不能证明：

```text
BM25 index = 215
```

两者是不同数据结构（Chroma 向量集合 vs BM25 倒排文档集合），必须
分别验证。因此 BM25 formal experiment 应单独证明：

```text
sparse_index_count == expected chunks
```

本项目契约：

```text
hybrid / bm25：sparse_index_count == vector_store_count == total_chunks
simple：       sparse_index_count = null（不依赖 BM25）
```
