## 能力边界收口的模式

SemanticChunker 的处理展示了"能力边界收口"的完整模式（G1-CHUNK-05B）：

1. **诚实标注**：类注释写明 EXPERIMENTAL + 具体已知限制（原文 Span
   不可靠 / 严格预算不可靠 / token decode 风险 / Embedding 对齐风险）；
2. **入口隔离**：正式实验入口（ExperimentConfig）拒绝该策略并解释
   原因，而不是在所有调用点逐个防御；
3. **保留出口**：普通应用 Config 仍接受，手动学习/调试入口不删除；
4. **状态登记**：status.md 策略状态表（stable / experimental 分层）。

关键：**不满足契约 ≠ 删除**——隔离 + 文档比静默放行或鲁莽重写
都更好。

## 文档收尾的原则（G1-CLOSE-06）

- 文档声称的能力必须与实现一致（SemanticChunker 注释首句
  "min/max 长度真实生效" 与实际状态矛盾 → 修正为"实验性实现"）；
- status.md 是唯一实时状态表：每个已验收任务转 ✅、测试历史用
  **本次真实全量结果**（而不是预测值）、验收基线更新到当前完成状态；
- 收尾任务本身不引入新测试——数字不变时如实写，不虚构增量。

## 从 Gate 1 到 Gate 2

Gate 1 的产出是"可信的基础 RAG"：检索、融合、元数据、上下文预算、
排名、分块全部有契约约束与测试锁定。下一步（Gate 2 / ExperimentRunner
入库）建立在"每个环节的结果都可以被信任"之上——评测对比的结论才
有意义。
