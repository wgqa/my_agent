# 100-Gate5：能力发现与前端降级

## Health 不等于 Capability

`/health` 主要回答服务是否能响应以及基础配置是否可读；它不保证每条业务链路都已初始化。`/capabilities` 返回运行时能力契约，分别声明 Basic RAG、Agentic RAG、Structured Tool Agent 和 indexing 是否可用。前端必须消费后者，而不是根据 health 状态猜测能力。

## Readiness 不等于 Liveness

服务进程存活（liveness）只说明 HTTP 进程存在。某个 pipeline、Planner runtime 或 Tool Agent runtime 可能仍未 ready。能力端点把这些独立 readiness 状态显式化，让产品层在用户提交之前做出正确提示。

## Graceful Degradation

能力端点失败时，UI 采用保守策略：保留 Backend health 的结果，但将能力视为 unavailable。这样 API 完全离线时仍显示“服务不可用”，health 成功而 capabilities 临时失败时则显示“Capabilities unavailable”，页面不会因为第二次请求异常而崩溃。

不可用模式不显示正常 `chat_input`，知识库在 `features.indexing=false` 时不调用 `/index/file`。失败在操作入口前暴露，比提交后等待一个 503 更清晰，也避免无意义的网络请求。

## Contract 如何进入产品层

后端 contract 的价值不只在 OpenAPI 或 API 测试中。`ApiClient.capabilities()` 保持唯一 HTTP 入口，`ui/app.py` 严格读取 `features.basic_rag`、`features.agentic_rag`、`features.structured_tool_agent` 和 `features.indexing`，再把事实映射为状态、门控和提示。前端不复制 runtime 初始化规则，也不从配置字段推断能力。

## 验证层次

单元测试验证字段映射和调用边界；AppTest 在真实 FastAPI 进程前执行页面脚本，验证 UI 确实消费 `/capabilities`；startup smoke 只证明进程和 health 可用。三者都不需要调用真实 LLM，避免把能力发现测试误变成模型质量测试。

## 面试表达

可以概括为：“health 证明后端活着，capabilities 证明哪些产品路径 ready。UI 在提交前消费 capabilities，ready 才显示输入控件；端点失败则 fail-closed 并保留 health 状态。这样 readiness contract 真正进入了产品交互，而不是停留在后端 schema。”
