# 62 - API 本地暴露与请求边界

> SEC-P0-01B：本地 Demo 的剩余安全边界 —— CORS 收口、默认只监听 127.0.0.1、Query 输入上限、/query 通用错误响应、01A 异常路径清理补测。
> 日期：2026-08-09

## 1. CORS 能解决什么、不能解决什么

CORS（Cross-Origin Resource Sharing）解决的是"**浏览器里跑的网页**能否跨源读取响应"这一层：

- 能解决：`http://localhost:8501`（Streamlit UI）页面里 fetch 到 `127.0.0.1:8000`（API）时，浏览器先看服务端返回的 `Access-Control-Allow-Origin`，来源合法才把响应交给页面 JS。
- 不能解决：curl、Postman、脚本、爬虫、后端到后端的调用——这些不受浏览器同源策略约束，CORS 头对它们没有任何拦阻作用。

所以 CORS 是**配合浏览器的一个展示/接入约束**，不是认证，更不是网络防火墙。没有浏览器参与的攻击面（直接打 API 端口）CORS 管不了。

## 2. 为什么 wildcard + credentials 不合理

`allow_origins=["*"]` 配合 `allow_credentials=True` 是组合反模式：

- `*` 意味着"任何来源都能拿到允许的凭证携带标志"；一旦同时允许 credential，浏览器会在跨源请求里带上 Cookie/Authorization，等于把凭证暴露给任意恶意站点。
- 更安全的服务端甚至会**拒绝 `*` + credentials 的组合**（浏览器规范也禁止 `*` 与 `Access-Control-Allow-Credentials: true` 同时返回，此时会被判定为失败）。
- 即使不携带凭证，`*` 也把允许的来源面放到无限大，任何站点都能发起并读取请求，与"本地 Demo"的定位冲突。

正确姿势：显式列出唯一需要的来源（`http://localhost:8501` / `http://127.0.0.1:8501`），`allow_credentials=False`，方法只开 GET/POST，头只开 Content-Type。

## 3. 127.0.0.1 与 0.0.0.0 的区别

- `127.0.0.1`（loopback）：只监听本机回环接口。外部机器无法建立连接，局域网里的其他设备也访问不到。
- `0.0.0.0`（所有接口）：绑定机器上所有网卡，包括局域网 IP。同网段任意设备都能访问该端口，等于把服务暴露给整个局域网。

本地 Demo 默认用 `127.0.0.1`：本机功能完整可用，误暴露面最小。`0.0.0.0` 只应在确定要对外提供服务时使用，且必须配合认证、TLS、反代、限流等部署安全配置。

## 4. Pydantic 请求边界

请求参数一旦允许任意值，攻击者或误用方就能构造超大、超长、非法输入，消耗内存/算力或绕过业务假设。Pydantic 在请求解析层做强类型 + 边界约束：

- `question`：1～4000 字符（`min_length=1, max_length=4000`）；
- `top_k`：1～50（`ge=1, le=50`），默认 5；
- `history`：最多 20 条，每条约束见下；
- `HistoryMessage.role`：用 `Literal["user", "assistant"]`，其他值直接拒绝；
- `HistoryMessage.content`：1～8000 字符，且校验器拒绝纯空白。

约束在**进入 handler 之前**就完成，非法请求返回 422，不会碰 Pipeline。这样上限规则集中在 schema，一处定义、处处生效，OpenAPI 文档也同步反映。

## 5. 为什么 top_k、question、history 必须有上限

- **top_k**：过大检索候选会放大检索/重排/生成开销，且对质量无益；无上限意味着客户端可任意放大服务端成本。
- **question**：过长问题没有检索价值，却消耗 token 与处理时间；限长能挡住恶意大输入。
- **history**：多轮历史无限增长会撑爆上下文与 token 预算；限条数 + 限单条长度，让上下文成本有界。

本质是"**成本与语义都受客户端不可信输入影响**"——服务端必须为这些输入定义可接受的边界，而不是信任客户端"不会传大值"。

## 6. 为什么 mutable default 应使用 default_factory

`history: List[...] = []` 这类可变默认值：默认 list 在**类定义时只创建一次**，所有没显式传 history 的实例会共享同一个列表对象。某个实例往里 append，会影响其他所有实例——这是经典的共享可变默认 bug。

Pydantic v2 用 `Field(default_factory=list)`：每次实例化都新建一个空列表，实例之间互不影响。测试断言两点：两个实例的 `history` 互不相同（`is not`），且字段的 `default_factory` 存在（契约级验证）。

## 7. 通用错误响应

`/query` 与 `/index/file` 的异常处理统一为一个原则：

- `HTTPException`（业务/校验错误）原样上抛，保留 400/413/503 等语义；
- 其他未知异常只在服务端 `logger.exception` 记录，客户端统一收到通用 500，**不返回** `str(e)`、本地路径、模型信息或 traceback。

`str(e)` 常含内部细节（文件路径、Key、依赖库信息），回给客户端等于主动泄露侦察信息；traceback 更是把代码结构完整交给对方。通用 500 让客户端只能知道"服务端出错"，排查细节留在服务端日志。

## 8. 本地 Demo 与公开部署的安全差异

| 维度 | 本地 Demo（当前） | 公开部署（未来，未实现） |
|------|------|------|
| 监听 | 127.0.0.1 本机 | 需反代 + 公网入口 |
| CORS | 白名单本机 UI | 按需收紧来源 |
| 认证 | 无 | 必须（登录/API Token） |
| 传输 | 本机 loopback | 必须 TLS |
| 限流 | 无 | 必须 |
| 上传 | 20 MiB 上限已加 | 需深度检测等 |

本地 Demo 的安全目标是"**把误暴露面降到最低**"（本机 + 白名单 + 输入边界 + 不泄露）；公开部署的安全目标是"**面向不可信网络的完整防线**"，二者不是一个量级。

## 9. 当前仍未解决的边界

- 认证/授权：无登录、无 API Token；
- 传输安全：无 TLS；
- 限流/防滥用：无（20 MiB 上传上限是大小限制，不是频率限制）；
- CORS 之外的访问控制：无 IP 封禁、无反向代理；
- MIME 深度检测、PDF 解压炸弹检测：仍按扩展名白名单处理；
- `/stats` 端点未做保护（任务明确不修改）。

这些都属于"公开部署前置条件"，在本机 Demo 阶段不实现，但要记录在案，避免日后误以为当前状态可对外。
