# LLM 调用失败语义与轻量可靠性

> G9-RELIABILITY-01：把生成器的 provider 失败从“看起来像答案的字符串”改成明确、脱敏的系统失败。

## 1. 为什么失败语义是接口契约

`Generator.generate()` 有两个不同的结果域：成功时返回非空答案字符串；失败时抛出异常。失败不能返回 `[生成失败: ...]` 之类的普通字符串，因为上层很容易把它继续放进 `QueryResponse.answer`、引用校验或 Agent history。这样会产生 HTTP 200、状态 completed 或“答案内容存在”，但实际没有完成生成。

当前公共错误定义在 `core/generator/errors.py`：

- `GeneratorAuthenticationError`：认证失败；
- `GeneratorTimeoutError`：超时重试耗尽；
- `GeneratorUnavailableError`：429、5xx 或连接/服务不可用；
- `GeneratorResponseError`：provider 返回结构不合法；
- `GeneratorError`：以上错误的公共基类。

这些异常只携带稳定的 `code`，不保存 API key、完整 provider 正文、raw response、prompt 或本机路径。稳定 code 适合日志、测试和边界映射；异常正文不应该成为 API 或安全 trace 的数据源。

## 2. timeout、retry 与错误分类

Timeout 是客户端在规定时间内没有拿到 provider 响应。Retry 是对同一个逻辑请求再次发起调用，通常需要有限次数和退避；它不是无限循环，也不是把失败转写成答案。

适合有限 retry 的通常是暂时性失败：

- timeout：网络或 provider 暂时变慢；
- 429：限流窗口可能很快恢复；
- 5xx：provider 服务端暂时异常。

当前 `core/generator/deepseek_gen.py` 保留原有 `max_retries` 语义和指数退避：429、5xx、timeout 按原策略重试，耗尽后分别得到 `GeneratorUnavailableError` 或 `GeneratorTimeoutError`。连接失败映射为 `GeneratorUnavailableError`，保持当前不新增重试策略。

Authentication 不适合 retry。错误通常来自无效、过期或权限不足的凭证；重复发送只增加等待和 provider 压力，不会修复凭证。因此 DeepSeek 认证失败立即得到 `GeneratorAuthenticationError`。OpenAI Generator 没有在本任务中重新设计自己的 retry policy，只对已知异常做同一套错误语义映射。

provider response 的 `choices`、`message`、`content` 也属于契约。缺失、空列表、非字符串或空白 content 映射为 `GeneratorResponseError`。这和网络暂时失败不同，不能靠重试修复格式契约。

## 3. Provider failure 与 programming bug

已知的 SDK 异常可以分类，是因为系统知道它们的边界和处理方式。未知的 `RuntimeError("programming bug")` 不应该被 `except Exception` 改名为 timeout 或 provider unavailable；生成器会让它自然向上传播，保留 fail-fast 的开发信号。

这里的“自然传播”与 Agent Runtime 的边界状态并不矛盾：`core/agent_runtime/runtime.py` 会把 AnswerPort 的生成异常统一转换为 `status="failed"`、`error_code="GENERATION_FAILED"`，但 safe trace 只保留 `GENERATION_FAILED`，不暴露 `GeneratorTimeoutError`、原始异常正文或 provider 响应。生成器层负责正确分类，Runtime 层负责稳定的 Agent 运行契约。

## 4. Fail-fast 与 graceful degradation

Fail-fast 是发现无法可靠继续时立即停止并暴露明确失败，避免产生假的成功结果。生成器 response 非法、未知编程错误属于这一侧。

Graceful degradation 是在不伪装成功的前提下给调用方稳定的降级结果。例如：

- `api/app.py` 的 Basic `/query` 捕获生成异常并返回 HTTP 500 与 `Internal query error`；
- Agent Runtime 返回结构化 failed result，`answer=None`；
- Tool Agent 对预算耗尽、工具错误或 provider 决策失败使用自己的结构化状态/失败码，真正违反程序契约的返回值仍 fail-fast。

降级的重点不是“总要返回 200”，而是让客户端知道请求没有成功，并且不泄漏内部细节。

## 5. 三条实际链路

### Basic RAG

`core/pipeline.py` 完成检索、上下文组装和 `generator.generate()`。它不吞生成器异常，也不把异常转换为答案字符串。`api/app.py` 在 HTTP 边界记录内部日志，向客户端只给通用 500 detail。因此 timeout 不再变成 HTTP 200 + 错误文本。

### Agentic RAG

`core/agent_runtime/adapters.py` 的 grounded AnswerPort 调用现有 Generator，并继续做引用校验；真实 Generator 的失败现在直接是 typed exception。`AgentRuntime` 将生成阶段异常转换为 `GENERATION_FAILED`，答案为空，API 保留既有 Agent response schema。生成失败 trace 的 exception type 归一为 `GENERATION_FAILED`，而不是 provider 子类名。

### Tool Agent

`core/tool_agent/runtime.py` 是独立的 Decision → Tool → Observation 有界循环。本任务不改它的预算、工具执行和 API 契约。它已有的决策失败、工具错误、重复调用和预算停止使用结构化状态；provider 返回违反 Runtime Protocol 时仍然 fail-fast。这个边界说明 Tool Agent 不是 Basic/Agentic Generator 错误语义的隐式复用点。

## 6. 为什么暂时不上 Circuit Breaker 或 Workflow Engine

当前问题是错误分类和接口语义错误，不是需要跨请求熔断、持久化恢复或分布式编排的问题。现有链路只需要：有限 retry、typed exception、API 通用错误、Agent failed result 和安全 trace。引入 Circuit Breaker、队列、checkpoint 或 durable workflow 会扩大状态空间和运维成本，却不能替代这一步的契约修复；等有明确的跨请求容量、恢复和一致性需求，再单独评估。

## 7. 面试中的解释方式

可以用一句话概括：**模型调用成功才产生 Answer，调用失败产生结构化系统失败；暂时性 provider 错误有限重试，认证和非法响应不重试，未知程序错误不伪装分类；HTTP 和 Agent 边界再分别做安全降级。**

这样既避免“错误字符串被当成答案”，也避免为了看起来稳定而吞掉真正的代码缺陷。
