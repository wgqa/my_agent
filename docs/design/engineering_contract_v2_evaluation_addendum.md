# Engineering Contract v2：工具评测后的实施范围补充

状态：**设计提案，未实施**。日期：2026-10-10。

经当前源码和离线行为复核，事实、错误更正与首期边界见 [证据需求与 Planner 架构复核](../validation/2026-10-10-evidence-architecture-review.md)。首期保持知识 Planner 独立，改造现有证据需求模块及材料/完成交接；不一次实施原 v2 大设计的所有能力。

定位更正：LLM 实现替代现有 Router 的需求解释职责，旧规则保留用于对照和明确回退；每轮只有一个有效需求来源，不额外串联两个需求模块。具体阶段、接口与 A/B/C 对照见 [LLM 替换与对比评测计划](engineering_requirement_llm_replacement_plan.md)。

本文补充已有的 [Task / Evidence / Execution Contract v2](engineering_task_execution_contract_v2.md)，依据 [工具调用首轮真实基线](../validation/2026-10-10-tool-call-evaluation-v2.md)收窄首个实现范围。沿用原设计的唯一执行循环、模型解释任务、系统登记来源、逐项完成报告，不另建一套 Agent 或任务契约。

首轮基线是冻结的 R01 版本；当前共享工作区已包含后续项目绑定与概览等改动。基线成绩不能直接当成这些改动后的成绩。本文没有重新调用模型，也不宣布任何新通过率。

## 1. 根因与解决方向

目前知识 Planner 负责知识库检索规划，工程 Requirement Router 独立决定工程证据要求，后者主要依赖关键词。完成校验以证据类别、路径数量与引用格式为主，不充分表达具体交付对象与材料深度。

这会同时产生两个方向的问题：

- 简单请求被要求提供不必要的正文。例如基线中 changed_files、find_tests 的 12 道目标题取得要求的列表或候选结果，却在最后被拒答。
- 复杂请求虽然取得某类证据，却遗漏用户指定的另一个对象、完整实现或关系位置。拥有一个 project_code 不能证明所有源码要求已经完成。

首轮自动 PASS 为开发集 27/48、新题 15/24；这些数字是工具路径与停止行为的结果，不是完整自然语言答案质量验收。两组分别有 13、7 道正向任务误拒答。原自动分及后续源码复核继续分别保留，不修改 Gold 来改善成绩。

建议将“需要什么”交给模型，将“真实取得什么”交给程序；用同一个逐项目标清单连接规划、工具观察、完成校验和用户反馈。放松所有护栏或不断追加问法都不能解决上述两类问题。

## 2. 首个切片的职责

| 环节 | 模型的职责 | 程序的职责 |
|---|---|---|
| 任务解释 | 证据需求模型从当前请求提取交付项、目标对象、需要的来源与材料深度；现有知识 Planner 继续负责知识检索规划 | 校验 schema、能力边界、请求与绑定身份，登记并冻结目标 |
| 工具调查 | 在已有权限和预算内选择下一步，根据实际观察定位对象 | 执行工具，登记真实调用、结果范围、版本、状态和截断 |
| 完成判断 | 按目标提交答案及依据，说明推断与未完成项 | 检查真实来源、对象匹配、可检验覆盖、引用和停止约束，生成逐项报告 |

模型的任务解释可能遗漏需求。schema 合法只证明格式合法；它不能证明模型理解完整，必须单独验收。模型也不能签发证据、改变权限、增加额度或把工具失败改成成功。

## 3. 材料需求随交付项变化

| 请求 | 所需材料 | 不能自动推出的结论 |
|---|---|---|
| 列出当前修改的文件 | 绑定仓库的真实 changed_files 结果 | 改动内容、影响范围、测试通过 |
| 找到某个函数的位置 | 对应对象的真实定位结果，明确候选或消歧状态 | 已阅读完整实现 |
| 找到相关测试文件 | 真实 find_tests 候选，标明候选身份 | 测试内容已核实或测试已执行 |
| 解释某函数的具体实现 | 对应对象实际读取的必要正文及范围 | 调用者或另一个函数的行为 |
| 分析某改动及相关测试逻辑 | 对应 diff、实际相关代码与测试正文，逐个目标核验 | 全库影响已穷尽或测试已运行 |

目标应包含交付描述、请求依据、来源要求、对象线索和覆盖要求。需要局部常量时有限行窗可以足够；要求完整实现时只读导入行不能完成。目标在本轮冻结，调查可以细化定位，不能删除必需目标或自动降低要求。

not_found、歧义、截断和错误是不同的观察状态。“当前限定搜索未找到”不能自动变成“全仓库不存在”；合法查找无结果也不应一律按安全拒答返回。

## 4. 接入模型的位置

**第一阶段改造现有证据需求模块，引入 LLM 替代实现，并保留旧规则实现；复用现有模型调用基础设施，现有知识 Planner 继续负责知识库检索规划。** 不把整个 Verifier 替换成模型。

Engineering 路径采用独立版本化的任务与证据需求输出。知识 QueryPlan 仍由现有知识 Planner 产生，保留其 schema、检索职责与历史评测；新增需求输出通过明确的校验及适配入口接入，不能给既有严格 JSON 随意追加字段。

当前最终校验是同步、严格返回类型的入口，不能声称给它塞一段提示词就完成集成。首个切片的校验仍执行确定性检查，Decision 模型依据目标及真实观察作语义解释。报告继续明确标注结构检查的范围，不把结构通过当成自然语言正确性证明。

若新评测仍显示“材料齐全但解释明显不受支持”，再比较一次有预算的最终语义审查。语义审查应放在受计数的模型阶段，输入实际可用材料，输出具体不受支持的陈述及材料引用；之后仍经过程序校验。模型审查超时或输出无效必须记录，不能默认通过，也不能启动无限修复循环。

模型审查也可能误判。它不能越过真实来源、权限和预算检查，亦不能替代独立的端到端答案评测。

### 4.1 替换实现与调用复用

当前 `EngineeringEvidencePlanner` 只是 `BaseQueryPlanner` 的一次委托，输出必须是已有 `PlannerOutcome`。已有模型解析器只接受 query_type、retrieval_required、action、reason_code 和 subqueries，当前失败计划会回到原问题单次知识检索。因此，不能直接复用这个完整对象来承载任意工程交付项，也不能将其旧知识 fallback 原封不动用于工程任务。

推荐给现有证据需求模块建立统一替换入口和版本化输出，保留规则与 LLM 两种实现，复用模型客户端、超时处理、调用统计及记录机制；严格解析的通用能力可以抽取，领域字段与降级策略独立。当前运行中知识 Planner 和 Requirement Router 本来就分别产出知识检索计划与工程证据要求，Router 不使用 Planner 的结果来决定 requirement。将 Router 的语义解释替换为模型，不会因此新增两份工程证据需求规划。

| 选择 | 优点 | 代价与风险 |
|---|---|---|
| 直接扩充旧知识 Planner | 接线较少 | 改动严格旧 schema 与历史兼容；知识分解和工程目标语义耦合，旧 fallback 不适用 |
| 独立工程模块，共用一次模型调用 | 职责和版本独立；需求与检索计划来自同一次任务解释 | 输出变长，可能相互干扰或遗漏；需检查两部分的一致性，新增解析及适配测试 |
| 现有证据需求模块采用 LLM 替代实现，单独调用模型 | 保持现有职责分工；需求解释、知识检索规划可以分别评测；旧规则可对照 | 增加调用与时延，需要输出校验、明确降级及统计 |

首期改为推荐第三项：保持现有知识 Planner 的职责和协议，单独升级证据需求模块。没有证据表明合并一次调用的质量更好，也没有理由为了假设的规划冲突改造现有知识 Planner。后续只有实际调用成本与时延需要优化时，再评测合并调用的收益和维护代价。

当前两个模块是职责不同的组件：知识 Planner 决定知识库是否检索以及如何分解检索，证据需求模块决定任务需要的工程材料。完成校验组合真实检索结果与证据要求。需求模块可继续独立解释请求，首期不要求知识 Planner 改成依赖新任务契约的接口。

知识检索子查询的 evidence_target 是知识检索范围内的目标，不是工程 requirement 的决定权；检索覆盖参与最终判断也不意味着存在两份工程需求裁决。先前将“两个独立模块可能冲突”列为缺点，混淆了这两种职责，现撤回该论据。仍需验证既有完成校验和新需求输出的兼容性，但这不是新增第二个模块才产生的需求冲突。

新需求调用必须有明确的超时、输出上限、失败处理与用量记录；不占用或扩张现有 5 次 Decision / 4 次工具预算，也不能隐藏额外 provider 调用。运行时预算和业务协议的必要接入改动单独验收。

从本轮基线的已知失败看，先接通列表、定位、候选等真实工具结果的来源登记与相应完成条件，有更直接的收益依据；同时继续按统一任务契约推进，不能靠为每道题加例外规则来适配。仍需新版本评测证明实际收益，不能声称仅增加一个 evidence kind 就已修复全部相关失败。

### 4.2 保留确定性、追踪与降级能力

旧 Router 的优点是同一问题与规则版本产生相同结构，运行快、无额外模型请求、可离线测试，规则分支可以定位。当前结果已有 router_version 与 requirement_profile，但没有逐项持久化全部命中词和判断过程；不能声称完整决策追踪已经具备。

新方案保留程序的确定性校验，将关键词判断从普遍的语义裁决收敛为明确的兼容路径与可检验约束：

- 模型只提交有界、类型明确的目标和请求依据，不提交权限、预算、证据身份或成功状态。程序校验目标结构、绑定和能力，将合法候选规范化为不可变契约。
- 必需目标在本轮冻结，不能因为难以取证而删除。程序按目标类型检查实际来源和可检验覆盖；格式合法仍不保证自然语言需求理解正确。
- 记录输入与解析后的上下文快照、任务契约与 hash、模型身份与调用参数、prompt/schema/校验策略版本、规划来源与失败码，以及工具结果和逐项裁决。模型返回的短理由只作为声明，不当成可靠思维过程；不保存思维链或敏感凭据。
- 追踪链明确展示“请求依据 → 目标 → 材料要求 → 实际来源 → 满足/缺失及理由”。目标理解错误、工具未取得材料、引用提交错误分别记录，便于定位。
- 模型输出无效时不能产生空目标并自动通过。允许的降级只发生在目标冻结前，按明确策略记录为旧规则兼容结果或规划失败；旧规则可能仍有误拒答，必须如实报告，不能当成智能新路径成功。冻结后不再切换需求权威。

可复现性必须区分两层：重新调用在线模型生成同一计划不能保证；保存计划、实际观察及版本后，确定性校验和评分可以离线重放。只冻结计划并不足以保证重新执行整个 Agent 得到相同结果，工具快照和后续 Decision 同样可能变化。

首期分别验收规划需求覆盖、同义表达稳定性、无依据额外要求、降级行为，以及固定契约与材料下的校验重放一致性。规则模式和模型模式在相同条件下对比，不能只统计总 PASS，也不能把 schema 合法率当成需求理解正确率。

### 4.3 需求输出不能停留在旧九种类别

现有 EngineeringEvidenceRequirement 的构造器把类别、证据组和路径数绑定为固定形状，不支持任意具名对象或材料深度。单纯让模型选择旧 profile，只能改善分类；首期还需要版本化表达定位、列表、候选、局部正文、实现正文及多个目标，并对接实际工具来源与覆盖判断。

模型的输入应保留当前请求与辅助指代的区别，不能把历史任务当成本轮要求。任务目标冻结，调查时允许细化尚未明确的对象位置；不能要求规划时预先知道所有文件和根因。

## 5. 保留与必要改动

保留现有 Decision → Tool → Observation 主循环、ToolExecutor、只读权限、取消与 deadline，以及默认 5 次决策 / 4 次工具 / 2 次错误。原 v2 设计中的扩容、写文件、运行测试和全链策略改造另行分阶段，不混入首个质量对比。

主要改动集中在规划装配、工具结果登记、逐项缺口反馈和 finalization 接口。必要的数据模型与接口适配属于范围内修改，不能承诺完全不碰 core 目录。

- 每个已有工具声明实际能提供的材料或凭据，登记绑定、对象、范围、状态与版本。列表和候选不得伪装成源码正文，也不得使用虚假行号来适配旧 evidence 类型。
- 同一目标进度用于下一步提示和最终校验。先区分“材料未取得”“材料不完整”“最终引用或提交有误”，避免拿到资料仍反复读取。
- 有剩余额度时在原循环内反馈具体缺项；引用修正与继续取证的恢复条件需要区分。没有额度时如实报告已确认部分和缺项，不另开循环补额度。
- 新模式中 TaskContract 是工程任务要求的唯一来源，旧关键词 Router 不再同时追加另一套要求。兼容模式在 run 开始前明确选择，本轮失败不能静默改用另一套规则。
- 首期不同时引入完整 partial 返回协议；先保持现有运行状态并验收正确取证与结束。元数据来源和新引用形式仍需明确 API/SSE 兼容投影。未来引入 partial 时不能压成 completed，也不能仅靠前端文案绕过校验。

当前现有元数据结果与 public evidence 的类型并不等价。因此，结果登记、引用表示和校验适配需要一起完成，单独放宽一条 citation 判断不是完整实现。

## 6. 实施与验证顺序

按一个完整的证据能力切片推进，每一步交付可单独检查的结果。新模式通过版本选择接入，旧模式保留为对照；不在运行中混用两套需求裁决。这里的任务契约只描述现有只读能力下的交付目标与材料要求，不建设通用工作流引擎。

| 顺序 | 实际交付 | 验收重点 |
|---|---|---|
| 1. 明确需求与材料接口 | 有界、版本化的目标结构；真实来源记录；旧正文证据的兼容适配 | 能区分“找位置”和“解释实现”；A/B 两个对象分别登记；列表、候选不伪装成正文；无效或空计划不默认完成 |
| 2. 接通已有工具来源 | 为定位、变更列表、测试候选和已有正文登记可引用来源；接通 core、API/SSE 与已有前端引用展示 | 列表任务可以根据真实列表结束；正文任务不能用列表或导入行替代；空结果、歧义、失败和截断分别保留；每条来源能追到实际调用 |
| 3. 接入 LLM 需求替代实现 | 当前请求与辅助指代输入、严格解析、冻结、版本与调用记录；先影子运行，再候选模式；保留旧规则对照 | 对同义问法、多个对象、材料深度、历史指代及能力边界分别评分；旧知识 Planner 的接口与职责不变；模型无效输出按声明策略降级或失败 |
| 4. 接通逐项完成与修正 | 同一目标进度进入 Decision 和 Verifier；区分继续取证与最终提交修正 | 有正确材料但缺引用时，能在剩余决策额度内有限修正；目标遗漏仍阻止完成；没有剩余额度时按现有状态返回明确缺项；额外模型调用不隐藏、不补额度 |
| 5. 冻结版本做真实对比 | 最新旧模式基线、新模式结果、原始调用与逐题错误分类 | 相同模型、仓库、知识库、预算和评分规则；旧题回归与新题验收分开；公开失败和耗时，不只报总 PASS |

步骤 1—4 作为一个首期实现包，不能只上线模型分类或放宽引用门槛。第一个可审查交付是需求/材料数据结构与离线纵向样例：列表、定位、完整实现和双对象任务使用同一交接方式，并包含错误材料不能完成的反例。影子阶段不会让新规划控制正式回答，也不证明实际通过率提高。

真实评测前先更新评测器对最新注册能力的身份记录，再冻结业务、题目和规则。旧 72 题用于诊断与回归；另建没有用于修改实现的新题作验收，不能继续把已公开的“新题集”当成独立未见验收。Gold 仅用于评分，绝不发给模型。首次运行用于看分布，多次运行用于衡量波动时保留每次结果，不选最好的一次。

比较任务完成率、误拒答、具体目标遗漏、无依据结论、错误引用、合法失败反馈，以及模型/工具次数、token 和时延。旧新路径保持相同模型、仓库、语料与默认预算，避免将增加预算的收益误归因于契约改造。

评测还应单独记录任务解释正确率和复杂答案的语义审查；工具调用目标正确、结构完成与答案质量是不同指标。全部原始失败保留，不取多次最优结果。

完成上述首期切片后，再单独建设第三层端到端评测：从实际产品入口提交请求，检查回答是否有材料支持、是否完整回应、引用是否可核验，以及多轮指代、拒答反馈和来源展示。工具层通过不能替代这一层，模型裁判也不能成为唯一依据。

首期不同时添加记忆压缩、新的项目挂载能力、第二个 Agent 循环、写代码/执行测试能力、完整 partial API 或预算扩容。真实对比有明确收益且负例未退化后，再决定默认切换；无效规划与兼容降级单独计数，不能记作新规划成功。当前没有足够依据预先承诺通过率目标。

本文仍为设计提案，没有实施生产逻辑变更，也没有启动新一轮真实评测。
