# 证据需求模块接入 LLM 的替换与对比评测计划

日期：2026-10-10。状态：**项目所有者已授权在本地基线提交并推送后实施；候选改造尚未开始，未启动新模型评测**。

实施前本地源码、版本及联合回归接缝复核见 [规则基线记录](../validation/2026-10-10-evidence-llm-baseline.md)。基线标签为 evidence-rule-v5-baseline-20261010，候选在 feat/evidence-requirement-llm-v1 分支分阶段提交，评测绑定具体 SHA 与运行配置。

## 1. 改造定位与范围

改造现有证据需求模块：引入 LLM 实现，逐步替代当前关键词/正则 Router 的需求解释职责。旧规则实现保留，用于历史兼容、对照评测和明确的回退。工程主链仍只有一个证据需求入口，每次运行冻结一份有效要求。

“独立”仅指证据需求职责独立于知识 Planner，不表示在现有 Router 后面再叠加一个需求规划模块。知识 Planner 的 QueryPlan、检索职责与调用协议保持原样。

目前的替换点是 `core/unified_engineering_runtime.py` 中对 `route_engineering_evidence_requirement(context_snapshot.lexical_query)` 的直接调用。接入后由该位置调用可配置的证据需求实现；不让旧规则与 LLM 分别追加要求，也不按宽松者放行。

| 部分 | 处理方式 |
|---|---|
| 旧规则 Router 与冻结 profile | 保留原实现及版本；通过适配入口使用，不继续按单道失败题堆问法 |
| 需求解释 | 由可切换的规则或 LLM 实现产生；LLM 路径表达具体目标及材料深度 |
| 材料来源与完成判断 | 补足现有严格接口，接受真实列表、定位、候选及正文，并逐项目标校验 |
| 知识 Planner / Retrieval | 保持原职责；只做新 requirement 与现有知识校验的兼容交接 |
| Decision → Tool → Observation | 保留唯一执行循环、ToolExecutor、权限、取消及默认 5/4/2 预算 |
| API / HTML | 适配新增材料的引用与缺项反馈，沿用当前 V2 stream；不同时重做页面或引入新 stream 版本 |

这是有限的核心接口改造，不是只改提示词。首期不扩展写文件、执行测试、记忆压缩或 GitHub 挂载，也不引入第二个 Agent 循环、完整 partial 返回协议或预算扩容。

## 2. 一个入口、两种实现与运行模式

实现名暂定 `RuleRequirementProvider`、`LLMRequirementProvider`，共同承担现有 requirement 的产生职责；模块与文件命名在接口评审时定稿。

| 模式 | 本轮执行所用要求 | LLM 需求调用 | 用途 |
|---|---|---|---|
| `rule` | 固定版本旧规则 | 无 | 当前默认、原行为回归与对照 |
| `shadow` | 固定版本旧规则 | 仅生成候选需求，独立记录 | 检查模型需求理解，不控制工具选择或最终完成 |
| `llm` | 校验并冻结后的 LLM 需求 | 有 | 候选实施与正式对比；评测默认禁用规则回退 |

模式由系统装配或评测进程选择，首期不增加用户页面上的模式开关。请求开始后模式固定，不随失败临时切换。影子模式增加实际调用与时延，因此必须计入统计，不能声称它没有运行成本。

另用内部 `evidence_policy=legacy|goal_v2` 区分原材料/完成接口与候选接口，默认组合为 `rule + legacy`。这样 A 组保留原转换和校验，B 组为 `rule + goal_v2`，C 组为 `llm + goal_v2`；不靠全局替换材料转换器来假装保留了原基线。非法组合在装配时拒绝，同一执行循环按固定接口策略工作，不复制第二套循环。影子阶段沿用 legacy 有效路径。

另设明确的 `fallback_policy`：

- 正式归因评测使用 `disabled`，LLM 输出无效、超时或调用失败按规划失败记录，不偷偷用旧规则修复成绩。
- 产品兼容试运行可使用 `rule_before_freeze`：仅在 LLM 要求尚未冻结且无法形成合法计划时，使用声明版本的旧规则；保存失败码与 `effective_implementation=rule`。
- LLM 返回了合法但语义错误的计划，不能因为工具取证困难而切换规则或删目标。这类问题进入需求理解评测。
- 冻结后不回退、不合并要求；整套产品退回 `rule` 是后续请求的配置选择。

影子比较使用同一个已解析的上下文快照。旧规则继续读取其现有 lexical 输入；LLM 输入保留 current_request 与辅助 reference_context 的区别。两者解释能力的差别应记录，不能让影子输出进入原路径的提示词、控制状态或校验条件。

## 3. 需求与材料的数据交接

### 3.1 需求输出

现有九种 profile 的结构不能表达具体对象和材料深度，LLM 替换不能停留在选择 profile。采用版本化需求表示，首期只覆盖已有只读工具的能力。

最小目标字段：

| 字段 | 作用 |
|---|---|
| `goal_id` | 程序规范化后分配的本轮稳定编号 |
| `deliverable` | 用户要求交付什么：列表、定位、候选、解释或比较等 |
| `request_basis` | 对应当前请求的可核验片段；辅助指代单独关联 |
| `target_hint` | 文件、符号、范围或尚未定位的对象线索，允许调查时消歧 |
| `accepted_sources` | 可支持该目标的实际来源类别，允许明确的替代组 |
| `material_depth` | 定位、列表、候选、局部正文或实现正文等深度 |
| `coverage` | 单对象、多对象或声明范围；所需对象分别检查 |

模型不能输出已完成状态、证据 ID、权限、工具额度或修改预算。必需目标冻结后不删减；调查可以细化对象位置，但不能将“解释实现”改成“找到位置”。

示例：“解释 A、B 两个函数的完整实现”必须保留两个对象目标，取得 A 的正文不能满足 B。模型不必在规划阶段猜出文件位置，后续定位属于调查步骤。

无需工程取证的请求必须有显式、可评分的需求声明；无效输出或解析失败不得降成空目标后自动通过。schema 合法率与语义理解正确率分别统计。

旧规则通过适配保留原 profile、证据组与路径数量约束，不借适配器补写旧规则没有识别出的具名对象。若旧约束无法无损表示，保留显式兼容分支并说明比较限制，不能悄悄降低旧约束来提高对照组成绩。

### 3.2 真实材料记录

所有材料 ID 与来源由程序从实际工具结果登记。首期继续沿用现有引用编号体系，并通过明确的类型分支表达正文和元数据，避免伪造行号或把列表塞进旧正文类型。

| 实际来源 | 可以支持 | 不能自动支持 |
|---|---|---|
| `code_search` 定位命中 | 声明搜索范围内的匹配位置、候选 | 完整实现或唯一对象身份 |
| `changed_files` | 返回范围内的文件状态列表 | 变更正文、影响或测试通过 |
| `find_tests` | 实际测试候选及匹配依据 | 已阅读测试逻辑、执行测试 |
| `read_project_context` | 实际读取对象、正文范围与完成/截断信息 | 未读取的另一对象或未覆盖正文 |
| `git_diff` | 返回的实际变更片段 | 未返回部分或运行结果 |
| 前置 Knowledge Retrieval | 当前知识材料及既有检索身份 | 当前仓库事实的直接确认 |
| `calculator` / `get_project_info` | 实际数值 / 平台绑定事实 | 源码正文；也不能被强制要求以正文形式表示 |

保留工具调用 ID、工具/结果版本、仓库绑定身份、实际对象与范围、结果摘要身份、截断及失败信息。公开投影仅给用户有意义的来源字段，内部绑定与记录信息不堆进页面。

“列出全部”需要检查返回范围和截断；合法空列表与调用失败不同。“未找到”只支持声明搜索范围内的结果，不能宣称全仓库不存在。被工具过滤的内容不通过本次改造解除限制。

Reader targets 已有对象与 content_complete 等实际结果信息，优先传递这些事实，而非新增一次模型判断来签发“完整”。对不能可靠确定对象或完整性的读取，保留 unknown/partial，不把它当成完整实现。

### 3.3 完成与引用交接

将逐项目标进度同时交给 Decision 和 Verifier，分别记录：目标未定位、缺材料、材料不完整、引用/提交不合格，以及满足的真实来源。

- 实际材料与被引用材料都要核对目标、来源和可检验覆盖，防止“读到了 A，却只引用别的文件”。
- 偶然检索到的知识材料不能自动制造额外工程要求；答案使用知识声明时仍保留既有知识引用控制。
- 新需求不能随意取消现有知识校验，知识要求与 QueryPlan/检索结果之间的兼容关系单独验证。
- 程序检查对象、范围和引用只能证明可检验的结构条件，不能证明整段自然语言解释正确；语义错误仍需要第三层评测识别。

## 4. 实施阶段与交付物

### M0：冻结当前事实和验收边界

1. 记录当前 HEAD、实际业务 SHA、工具注册/启用集合、模型及 prompt 版本。R01 的 56.3% / 62.5% 只作历史问题依据，不当作当前最新基线。
2. 明确列表、定位、候选、实现正文、多目标及工具事实的能力表和正反例；需求 Gold 不进入模型输入。
3. 确定 v2 需求、材料、完成结果的接口和回退策略。保留历史规则版本，不修改旧报告或原始结果。

交付：接口说明、能力/反例清单、实验分组和冻结清单。进入下一阶段前能明确区分“模型需求错误”“工具没有取到材料”和“提交格式错误”。

### M1：把现有 Router 包装成可替换入口

1. 装配层注入 requirement provider，默认 `rule + legacy` 仍委托原 Router 及原材料/完成接口；保留原规则 profile、输入与约束。
2. 运行模式、有效实现、版本与失败结果显式建模，默认继续使用 `rule`。
3. 在候选路径定义 v2 数据类型与兼容适配，检查 Runtime、Verifier、结果类型的严格校验限制。

交付：统一替换入口及规则适配。验收：规则模式不增加模型调用，已有行为回归保持，知识 Planner 协议不变。此阶段不宣称质量提升。

### M2：接入 LLM 替代实现，先做影子验证

1. 复用模型客户端与通用调用机制，独立实现需求 prompt、严格解析、规范化和冻结；不复用知识 QueryPlan 的领域 schema 或知识 fallback。
2. 输入只包含当前请求、有限指代上下文和真实能力说明；不依赖模型提前知道未知文件与根因。
3. 独立设置 timeout、输出/目标数量上限与失败码。初期不增加自动需求修复模型循环；这些参数在真实比较前定稿并冻结。
4. 记录每次需求请求的调用次数、token（未知单列）、耗时、prompt/schema 版本、输入快照身份及有效实现。需求调用不计作 Decision 次数，但计入实际 provider 总调用和用量。
5. Fake/Scripted 验证超时、非法 JSON、额外字段、空/超限计划、回退与取消；影子分析同义表达、多对象、材料深度和历史指代。

交付：LLM 实现与影子需求差异报告。验收：合法格式与语义理解分开评分，影子结果不改变原执行语义。当前执行 deadline 从 ToolAgent 阶段开始，新增需求调用必须有自己的超时，不能宣传已有全链硬期限。

### M3：接通工具材料与逐项覆盖

1. 从现有真实工具结果登记列表、定位、候选、正文及事实来源；传递已有截断与对象信息。
2. 接通 v2 目标、材料及 API/SSE 的类型适配；HTML V2 活动与资料区域能正确显示元数据来源，不生成虚假行号链接。候选转换与校验由 goal_v2 策略启用，legacy 不受其全局副作用影响。
3. 先用固定需求和 Scripted Decision 做纵向验证：四类基本任务能正确结束，缺 B、错误文件、导入行、截断正文和候选冒充正文均不能完成。
4. 为规则兼容计划与 LLM 计划使用同一套候选材料/覆盖基础设施；适配差异明确记录。

交付：真实来源到目标进度、最终引用及页面展示的完整通路。验收：来源能追到实际调用；不以增加 evidence kind 代替覆盖检查。

### M4：改造完成反馈和有限恢复

1. 将恢复类型区分为继续取证与修正提交，分别计算是否还有合法下一步。
2. 对材料满足但缺引用等可修正提交，允许最多一次使用剩余 Decision 额度的修正，不要求仍有工具额度，不另开模型或工具循环。
3. 继续取证仍遵守工具预算、权限、重复调用和无进展约束；不能因最终提交修正而重置它们。
4. 保持 completed/refused/failed 状态及 answer 不变量，通过安全的缺项反馈改善非完成结果。首期不把已有确认部分包装成新的 partial 答案状态。

交付：逐项完成结果、恢复原因与用户可理解的缺项反馈。验收：正确材料加缺引用的用例可以有限修正；额度用尽、引用仍无效、目标缺失均不会被绕过放行。

M1—M4 是同一个实施包。单独上线 LLM 分类、放宽引用门槛或注册元数据，都不算此包完成。每阶段可独立审查，候选模式在完整通路通过后才参与默认切换讨论。

### M5：真实对比、结果归因与默认切换

使用第 5 节分组和指标，先跑最新规则基线，再对照候选；正式模型评测前向用户说明范围。评测期间业务身份变化则停止并保留记录，不混合不同版本。

交付：版本清单、逐题结果、调用记录、离线重算、需求理解复核、错误分类、成本与时延对比，以及默认切换建议。通过条件见第 7 节，不能按结果修改 Gold。

## 5. 对比实验设计

仅比较“原系统”与“全部改造后的系统”可以看总体收益，不能证明收益全部来自 LLM。因此分组如下：

| 组 | 需求实现 | 材料与完成基础设施 | 用途 |
|---|---|---|---|
| A：最新原路径 | 当前冻结的规则实现 | 当前原路径 | 最新基线；保留原行为与严格约束 |
| B：规则候选路径 | 同一规则实现，显式兼容适配 | 候选来源登记、覆盖与提交恢复 | 看接口/完成机制改造的影响 |
| C：LLM 候选路径 | LLM，回退禁用 | 与 B 相同的候选基础设施 | 与 B 比较需求替换的影响，与 A 比较总收益 |

B 不能为了产生漂亮结果获得人工补写的题目目标。若兼容分支并非无损映射或不能使用一致的候选检查方式，报告差异，缩小归因范围，不能把 B/C 当成完全同构的因果实验。

启用规则回退的产品运行另报有效实现比例与总体结果，不并入 C 的纯 LLM 成绩。影子输出仅用于需求分析，不记作完成了工具任务。

题集安排：

- 旧 72 题作已知问题诊断和回归，其中原 24 题已经公开，不再声称是未见验收。
- 建议新增 24 道未参与实现调试的题，按六组各四题：列表/状态、定位/歧义、测试候选/正文、局部/完整实现、多对象/混合来源、多轮指代/能力边界。各组纳入合法空结果、缺项、截断等负例；评分条件在运行前冻结。
- 首轮各组每题一次，失败全部保留。稳定性另选预先固定的 12 题各跑三次，报告每次与分布，不取最好一次；普通任务重试不混入初次通过率。
- 需求解释可在同一已解析输入快照上直接对比；完整 Agent 对比共享模型参数、源码/知识库身份、初始状态与默认预算，但不声称在线模型可完全复现。

更新现有评测器的 toolset 与观察白名单，记录实际最新能力，不沿用 R01 六种主链工具的静态假设。知识检索仍走前置 Retrieval，不重新启用主循环 knowledge_search。

## 6. 指标、记录与离线验证

| 维度 | 检查内容 |
|---|---|
| 需求理解 | 格式有效率、必需目标召回、无依据额外要求、对象/深度正确性、同义表达一致性与规划失败 |
| 工具过程 | 合法参数与真实目标、材料取得、逐项目标覆盖、重复/无效调用、停止行为 |
| 完成质量 | 误拒答、缺项却完成、错误来源/引用、合法未找到反馈、提交修正是否有效 |
| 边界 | 越界尝试与实际拦截分别计数，不能把护栏拦截写成模型没有不当尝试 |
| 代价 | 包含需求、知识 Planner、Context、Decision/repair 的实际调用与可用 usage；工具次数、全过程 p50/p95，缺失用量不填零 |

当前产品公开 token 统计主要来自 Decision，本次不能直接把旧字段解释成全链总用量。首期至少在评测记录与内部阶段统计中完整计入新增调用；公开 metrics 如要扩展，使用明确的新字段并保留原字段含义。

保存需求契约与 hash、实现和版本、模型参数、上下文快照身份、实际工具结果白名单、绑定/对象/范围、引用及逐项裁决。公开记录不包含思维链、原始模型文本或凭据。固定计划与固定材料必须能够离线重放校验；重跑在线规划不承诺得到同一计划。

离线验证至少包括：

1. rule 原行为和不增调用；shadow 不改变有效要求；LLM 无效输出、超时与回退身份。
2. 当前请求与历史指代区分，具名 A/B 不丢项，同义问法与无依据额外目标。
3. 列表不冒充正文、候选不冒充测试内容、错误文件/导入行不完成、同名歧义与截断保留。
4. 已有材料的有限引用修正与继续取证分别受预算控制；未知引用仍不通过。
5. Runtime/Verifier 严格类型、API union、V2 stream、HTML 引用及非完成反馈兼容。
6. 评分器识别错目标/深度、失败和缺测；固定记录重算一致；版本或记录缺损不得静默通过。

复用现有相关测试和本轮 177 项离线审查作为起点，再增加上述确实验证新边界的用例，执行改动所适用的现有 CI 检查。177 项通过是改造前审查结果，不是此计划已实施或已通过的证据。

## 7. 切换条件与风险

默认仍为 rule + legacy。候选改造完成后的切换条件：

- 接口、相关回归及上述负例通过，旧模式仍可运行；权限、预算、来源真实性及引用校验不退化。
- 最新规则基线和 LLM 候选都完成冻结题集；对未见题展示实际收益，对误拒答、漏目标及无依据完成分别复核。不预先承诺 90% 或其他通过率。
- 能说明收益来自需求解释还是材料/完成适配；规划失败和回退不隐藏在平均数中。
- 调用与耗时完整记录，失败反馈可用，切回 rule 的装配测试通过。
- 样本不足或结果不稳定时保持候选状态，补充固定实验，而不将开发集提升直接宣布为正式泛化达标。

主要风险及处理：LLM 漏需求由独立目标 Gold 与未见题发现；格式合法但理解错误不能靠 schema 证明；旧规则兼容映射不能悄悄放宽；材料完整性不明时保留缺项；引用修正不能获得额外预算；同仓库其他改动需重新冻结身份。复杂答案的语义正确性仍是第三层评测的工作，不由结构检查包办。

## 8. 预计修改位置与工作约束

| 位置 | 预计修改 |
|---|---|
| `core/engineering_requirements.py` 及新增需求实现/模型文件 | 保留旧规则，增加统一入口、LLM 实现、版本化需求与兼容适配 |
| `core/unified_engineering_runtime.py` / `api/app.py` | provider 注入、模式选择、冻结与阶段记录、知识交接 |
| `core/tool_agent/runtime_models.py` / `runtime.py` / `decision_prompt.py` | 真实材料类型、来源登记、逐项目标进度及有限恢复 |
| `core/engineering_verification.py` | 新需求/材料覆盖、引用绑定与恢复类型；保留旧模式 |
| `core/tool_agent/activity.py` / `api/schemas.py` / stream/feedback 适配 | 新来源的公开投影、缺项反馈；沿用 V2 stream 和现有状态 |
| `frontend/js/app.js` / `activity.js` / `feedback.js` | 材料类型与引用展示、缺项信息兼容；必要样式另列 |
| `evaluation/tool_calls_v2/` / runner / 相关 tests | 最新能力记录、模式选择、分组对照、需求评分和离线重算 |

文件划分是计划而非已存在接口。实现前根据实际类型依赖收敛，不建立通用任务工作流框架，也不顺手改知识 Planner。

沿用用户已确定的同 checkout 协作方式，不新建业务 worktree；不覆盖另一对话改动。测试 fixture、知识库、登记/会话数据库与输出使用工作区内专用目录，不向当前 8000 服务发评测请求或重启它。正式模型评测前告知，并冻结实际业务身份；本计划本身不执行提交或推送。

首个实施交付为 M0/M1 的接口与规则兼容入口，随后完成 M2—M4 的纵向切片，最后进入 M5。第二层结果完成后，再单独补第三层从产品入口到最终回答的端到端评测，不把工具层通过率代替答案质量。
