## 1. 要交付什么

为当前产品建立一套能运行、能评分、能复核的工具调用基线，回答四个问题：

1. 模型是否采取合理的工具动作，参数和目标是否正确？
2. 工具返回是否真正取得任务需要的材料，而非仅有一次调用或一个路径命中？
3. 多步任务、可恢复错误、缺失材料和不允许操作是否得到正确处理？
4. 这些行为消耗多少逻辑决策、工具调用、实际 provider 调用、token 和时间？

本轮评工具执行过程与停止行为。完整答案的事实正确性、推理完整性、claim-level grounding，以及 HTML、上传/删除、项目切换和多轮产品链路归第三层。保留最终公共答案便于后续复用，但不从 `completed` 推导端到端成功率。

## 2. 当前运行方式：七个注册工具，六个主链可调用工具

主基准复用 `api/app.py::_build_engineering_project_runtime` 的实际装配及 `EngineeringAgentFacade`，保留 Context → Planner → 前置检索 → Decision/Tool/Observation → Guard 的完整业务路径。

正式配置为 Decision current_request v5、Planner references v3、Context references v2、`code_search_v7`、`read_project_context_v4`，预算仍为 5 次逻辑决策 / 4 次工具调用 / 2 次工具错误。单轮无历史，不触发 Context 模型调用。

| 工具 | 当前 Engineering 主链 | 评测处理 |
|---|---|---|
| calculator | 模型可调用 | 数值执行、表达式参数与错误行为 |
| code_search | 模型可调用 | 检索词、artifact kind、实际命中目标 |
| read_project_context | 模型可调用 | path + target、真实正文范围、定义、歧义与截断 |
| changed_files | 模型可调用 | Git 模式与真实变更文件集合 |
| git_diff | 模型可调用 | 路径、模式、实际 patch 与来源 |
| find_tests | 模型可调用 | 候选测试与后续测试正文获取 |
| knowledge_search | 已注册，但主链运行时禁用 | 七工具离线契约覆盖；不计入主链模型调用的预期覆盖分母 |

`core/unified_engineering_runtime.py` 实际传入 `disabled_tools=("knowledge_search",)`，Runtime 会过滤模型看到和执行的工具集合。知识由前置 Planner/检索组件获取，记录为 `pre_retrieval`，不能算成模型调用 `knowledge_search`。

不为评测重新开放该工具，不绕过 Planner/Guard，不使用旧 Gate 4 runner 冒充当前产品路径。如果以后需要真实模型直接调用七工具的组件实验，应使用单独的实验身份和报告。

## 3. 题集与覆盖：建议 48 题开发集 + 24 题新题验收集

题量按六工具的参数、目标和多步变体安排。新增题目必须测不同目标或行为，不以同一题改写措辞凑数量。

| 任务组 | 开发集 | 新题验收集 | 覆盖内容 |
|---|---:|---:|---|
| 六个可调用工具的目标任务 | 24 | 12 | 每工具分别 4 / 2 个观察机会；不要求只能调用该工具 |
| 多步取证 | 12 | 6 | 未知路径定位后读取、跨文件配置、文档/实现两侧、变更/测试、同文件多定义 |
| 缺失、歧义、截断与恢复 | 6 | 3 | 材料不存在、同名定义、有限续读、可控工具错误 |
| 无需工具与安全边界 | 6 | 3 | 合理直接回答、不支持的写入/执行、路径边界、不可信材料诱导 |
| **合计** | **48** | **24** | **72 个单轮用户请求** |

开发集采用小型可控 Git fixture 与已有固定 Requests 仓库（`b25c87d7cb8d6a18a37fa12442b5f883f9e41741`）；fixture 的 staged/unstaged 改动和所有预期材料都封档。

新题验收仓库使用 [urllib3 2.5.0](https://github.com/urllib3/urllib3/tree/2.5.0)，固定 commit 为 `aaab4eccc10c965897540b21e15f11859d0b62e7`。离线实施已下载固定源码并验证实际只读工具；没有执行该仓库测试或调用模型。来源、许可文件 SHA 与声明的 fixture patch 保存于 protocol。这是与 Requests 相关的 HTTP/Python 仓库迁移，不宣称跨领域泛化；新题和目标不复用开发题。版本参考：[官方 2.5.0 文档](https://urllib3.readthedocs.io/en/2.5.0/)。

先固定问题、输入文件、期望材料和规则，再运行模型。验收集不用来调 Prompt/规则；任务目标、题目及 Gold 与开发集做重叠检查。它是“未参与本轮调试的新题验收”，同一开发助手评分时不能称为独立人工评审或 sealed Holdout。

题目默认单轮，避免把 Resolver/多轮问题混入工具选择基线。所有正向任务须先证明目标材料确实存在、允许读取，并有一条在 5/4/2 内可达的路径；无法满足的任务标作边界或预算实验，不能作为普通正向题。

重点任务（已写入题集，Gold 可离线检查）：

- 不给文件路径，只给项目行为或定义线索，定位并读取真实实现。
- 已知路径，读取配置默认值和调用位置；允许直接 Reader，无需强制先搜索。
- 已知测试名读实际限定定义；只有候选路径或导入行不算取得测试正文。
- 未知变更路径时取得变更集合、diff、关联测试和测试正文，控制在最多四次调用。
- 路径已知时接受 `git_diff → find_tests/测试搜索 → Reader`，不强制 `changed_files`。
- Reader 覆盖 file/window/definition/symbols/matching，包含长文档后部、多片段、同名定义和续读。

## 4. Gold 与评分：评目标和必要依赖，不锁死唯一序列

每题保存 `case_id / split / project_id / query / task_group / observation_focus`，以及下列评分信息；全部 Gold 只供评分器使用，不进入模型 Prompt。

| Gold 内容 | 用途 |
|---|---|
| 必需目标材料 | 指定允许的源路径、定义、正文范围、diff 或数值结果，并绑定内容哈希 |
| 等价路径和替代材料 | OR 关系接受合法替代；AND 关系表达所有必要目标 |
| 参数约束 | 区分 schema 合法与实际 path、mode、artifact kind、target 正确 |
| 必要依赖 | 只约束真实依赖；可独立取得的材料不要求固定先后 |
| 停止预期 | 完成、合理拒答或明确材料不足；明确允许的原因类别 |
| 错误场景 | 是否注入、触发条件、错误码、可用替代及期望恢复目标 |

“调用过”与“取得了”分别评分。搜索候选、Reader 完整正文、Git patch、测试候选及测试正文不能互相代用；测试工具只读，不能据此声称执行过 pytest。额外的合理步骤不直接判整题失败，另列冗余与调用成本。

执行参数采用规范化路径/枚举/目标结构判分，不对搜索词做简单字符串相等。需要语义判断的查询词或新的合法路径进入源码复核，不凭关键词命中宣称正确。复核裁决另存理由及 `reviewer_type`（开发助手/项目所有者/其他评审），原自动分保留；真正 Gold 缺陷用新版本修正，不覆盖原题集和结果。默认由开发助手复核的内容不能标作人工或独立评审。

## 5. 报告指标与分母

| 指标 | 分母与解释 |
|---|---|
| 首次结构化动作有效率 | 有可用决策观测的逻辑决策数；利用现有 initial parse/repair metadata，单列修复后有效率 |
| 合理首个动作 | 有明确首步约束的题；按返回的已解析首步评分，单列是否经历解析修复；其余题 N/A |
| 参数错误 / 目标正确率 | 解析层 ARGUMENTS_SCHEMA_INVALID 与执行层参数错误分别记录；目标正确率针对已解析调用，有语义疑义时源码复核 |
| 必需工具调用覆盖 | 仅在确有不可替代工具义务的题统计；允许替代的能力不硬算成唯一工具义务 |
| 必需材料获取覆盖 | 冻结的目标义务数；同时给 micro 覆盖和整题全覆盖率 |
| 合法多步过程 | 多步题数；检查必需材料和依赖，不做唯一精确序列匹配 |
| 恢复率 | 实际触发且预先定义为可恢复的错误题；未触发单列，不算成功恢复 |
| 停止行为 | 各任务组的合理完成/拒答、误拒答、缺材料却结束等机械行为 |
| 边界行为 | 区分模型不当尝试与护栏成功拦截；两者不能合并为“模型安全通过” |
| 预算、重复、工具错误 | 全部有效题；模型解析失败、循环、超预算保留为失败 |
| 调用和消耗 | Planner + Decision（含解析修复）实际 calls/input/output tokens；逻辑步数另列 |
| 延迟 | 单题全过程与工具耗时、p50/p95；顺序小样本观测，不当作 SLA |

逐题给出过程 PASS / PARTIAL / FAIL、未满足义务、失败阶段和原因；硬性越界单独列出。`completed/refused/failed` 原始状态同时保留，不代替评分。

报告并列计划请求数、实际请求数、有效记录数、基础设施无效数与未运行数。网络/provider 不可用、记录器故障与模型/工具行为失败区分；无效项不能静默删除。没有观察机会或分母为零时显示 N/A 和覆盖不足，不填 100%。解析失败导致工具名不可可靠识别时，全局列参数错误和未知归属，不从原始模型输出猜测。汇总按任务组、工具、仓库、开发/验收分别展开，不把二者或历史版本混成一个成功率。usage 缺失标为未知，单列缺失调用数，不当作零 token。

## 6. 如何记录与复现

在独立评测进程中复用当前装配入口，被动包装 Decision Provider、ToolExecutor 和前置规划/检索；委托原实现，记录调用前后事实。不修改 `core/`、生产 API 或前端。少量故障注入仅在声明的专用场景和隔离 handler 中生效，其结果与普通任务分组。

不能只依赖 HTML V2 Activity：公开活动有截断/字段白名单，当前 Reader 的完整 `target` 和多片段细节不都在其中。评分使用执行层记录的白名单参数、实际结果与来源定位，Activity/trace 作辅助。

记录范围：模型已经解析出的动作类型、合法工具参数、工具状态/错误、实际路径/定义/正文范围/数值/patch、public evidence、停止状态、调用 metadata 与耗时。不保存 Prompt、思考过程、原始模型输出、真实凭据或本机绝对路径。观测缺失必须显式判为记录不完整。

`run_manifest` 冻结：

- 被评代码 HEAD 与实际业务文件 SHA；评测器版本、题集/Gold/评分规则 SHA。
- provider/model、Decision/Planner/repair 身份、输出 cap、预算、deadline 和重试配置。
- 注册工具与运行时可调用工具的名字、版本及 schema SHA。
- 源码仓库 commit、声明的 fixture patch、文件内容哈希、Git 初始状态。
- 独立 managed 知识库输入文档、分块配置及实际内容身份；不只记录“37 篇”。

独立项目目录、知识库、会话/登记数据库与输出目录均放工作区内。复用基础语料构建隔离 managed 库，冻结已纳入评测的输入；不触碰生产库。运行前后检查源码和 fixture 状态。数据集版本、代码版本或 Prompt 改变即建立新实验，原结果不覆盖。

### 与同项目其他对话并行工作

项目所有者目前另有一个活跃对话定位 bug，8000 端口服务也已运行。按 2026-10-09 的明确指示，本轮在同一 checkout 中新增评测文件，不另建业务代码副本或 worktree。评测数据和临时数据库仍使用专用目录。

- 评测脚本开发、pytest 临时目录、fixture Git 仓库、managed 知识库、会话/登记数据库与报告都使用专用目录；不得复用另一任务的 `--basetemp`、runtime 数据或输出目录。
- 不通过当前生产 8000 服务发送评测请求，不停止或重启它。主基准直接调用评测进程中的 facade。
- 复用已安装包，不安装/升级共享 Python 环境；不在原工作目录切换/reset 分支或清理其他任务的文件。
- 只新增评测外围文件；若另一边修改业务代码，重新计算实际 SHA。正式运行前冻结版本，运行期间版本变化则停止并保留记录。
- 默认串行调用模型。CPU、内存、磁盘和同一 provider 的额度/限频仍共享；隔离不意味着完全没有资源竞争，必要时调整运行节奏。

另一任务期间新增的业务改动不自动属于本轮快照。报告记录被评 commit/实际 SHA 与当前版本差异；涉及工具或装配的新改动在冻结新版本后复测，不能将旧快照结果写成最新代码已验收。

## 7. 执行阶段

| 阶段 | 工作 | 进入下一阶段的条件 |
|---|---|---|
| A：计划讨论 | 确认题量、六工具主链边界、新题仓库及评分方式 | 已授权进入离线实施；正式模型评测前告知 |
| B：离线实现 | 新 schema/题集/fixtures/观察器/评分器/runner；验证 Gold 可达及错误样例能被识别 | 零模型预检与有意义的评分器测试通过，题集/规则冻结 |
| C：开发基线 | 先跑四个预选开发题检查记录链路，再跑余下 44 题；全部每题一次 | 记录完整、版本一致；模型失败照常保留 |
| D：新题验收 | 同一冻结业务版本跑 24 题，审查疑难/失败及抽查通过项 | 自动分、复核裁决与评审身份、原始事实和汇总可追溯 |
| E：结果交付 | 给出指标、逐题失败、成本、能力边界与下一步修复建议 | 能离线重算分数；不以漂亮数字作为完成条件 |

四题预选包含一个基础工具、一个多步任务、一个 Reader 复杂目标和一个边界任务；是 48 题的一部分，不再重跑充数。评测器缺陷导致的无效运行保留，修复后的补跑使用新记录与显式原因；不因模型答差自动重试挑结果。

开发与验收之间不改生产策略。如果后续授权修复系统，先形成新业务版本与新开发结果，再执行仍未用于调试的验收题；不得把前后版本混在一次报告中。

默认单轮、顺序执行。上限为 72 次正常用户请求；不是 72 次 provider 调用。按当前每题 1 Planner + 最多 5 Decision、每次 Decision 最多一次解析修复，理论最多 11 次 provider 调用/题，即 792 次；实际以 metadata 为准。保留生产原有解析修复，评测器不加额外任务重试。本轮不做并发压测或反复抽样稳定性实验。
