## 1. 执行原则

完整问题清单保留。每次实际开发围绕一个明确根因，按“复现 → 最小必要修改 → 局部回归 → 对比结果 → 交付结论”闭环，不将多个独立问题混入一次改动。

一个问题可能需要修改几处关联模块；边界由同一个根因和验收目标决定，不用“只改一个文件”衡量。顺带整理目录、升级其他能力、改动无关 Prompt 或调整其他策略，不进入当前切片。

优先复用现有接口、Reader、绑定记录和结果存储。尽量保持单一 Agent 循环、5 次逻辑决策 / 4 次工具调用 / 2 次工具错误、Executor、权限边界、Evidence / Citation 校验和终态机制。若确实需要改变核心机制，先单独说明原因、行为影响与代价，再形成可审阅的设计，不在普通 bug 修复中顺手重构。

不预先把“无新增工具”“不增任何字段”设为绝对限制；是否需要由各问题的证据决定。新增能力必须有独立验收，不能为了一个案例扩大整个控制链路。

## 4. 首次开发只处理 R01

### 4.1 问题边界

首片实施时的唯一问题是：历史补全结果覆盖当前请求动作。该问题收口前，不同时增加项目检查工具、导航、绑定界面、知识库状态或历史引用查询，也不顺带完成 R06 的完整诊断页面。

### 4.2 拟实施办法

- 复用已有 `EngineeringContextSnapshot.original_input` 和 `resolved_input`，保留当前请求及辅助补全，明确各自职责。
- 当前请求决定本轮目标和动作；历史用于解释“它、刚才那个”等对象引用。相同项目可以承接不同任务，不能以“话题相同”覆盖当前动作。
- 在现有 Engineering 交接及 Prompt 输入中实现上述职责；不能只优化 Resolver 提示后就假定它不会产生合法但错误的改写。
- Planner、Router、Decision 相关修改仅服务于这一请求交接问题。保留 QueryPlan 字段、Parser、fallback、identity 一致性和单次规划；不把新旧两句简单拼成一个路由查询，导致旧任务扩大本轮证据要求。
- 真正的承接追问继续使用对象补全；不能简单删除拒答历史、取消改写或把全部 resolved_input 替换成原句。
- 只更新实际变化的 Engineering Prompt 版本/hash；保留原配置用于对照。诊断优先使用现有观察接缝及测试捕获，不在首片扩成一套观测系统。

允许涉及的范围是同一输入问题的必要交接处。ToolAgentRuntime 的循环、预算、停止条件、Executor 和最终校验策略不属于首片修改目标。

### 4.3 首片验收

| 场景 | 验收要求 |
|---|---|
| 目录问答后“说一下目前的项目” | 实际规划/执行仍面向介绍项目，不替换为目录问题 |
| 注入合法 JSON、语义错误的改写 | 下游仍保留当前请求；错误辅助信息不能直接替代当前任务 |
| 同一项目连续更换动作 | 继承项目对象，保留本轮动作 |
| “它的默认值呢”等真实追问 | 有历史时能补全对象；既有有效追问不回归 |
| 拒答后明确补充对象 | 能使用补充，不延续旧拒答结论 |
| 多个对象后的模糊“它” | 不能凭空选择目标；如实追问 |
| 源码问题后切换通用技术问题 | 不继续执行旧文件调查 |
| 无历史及原配置/文档/变更任务 | 原输入、来源要求和 5/4/2 保持有效 |

先做错误改写注入和接缝的局部离线回归，再告知项目所有者并用少量真实模型请求对比。保留原结果与失败，不通过重试筛掉失败记录。

首片收口要报告：改写前后、下游实际任务、工具动作、终态、消耗和已知限制。仅证明原句出现在 Prompt 中还不够，必须核对实际任务没有被覆盖。

R01 的完成不等于 R02/R03 自动完成：即使任务保留正确，项目概览仍可能因为缺少资料入口拒答。必须如实区分“动作交接已修复”和“最终答案仍缺某项能力”，避免把后续问题混入首片或宣称整条链路已修好。

## 6. 全局约束与最终对照

项目根目录、项目身份和会话身份由服务端确定，不能由模型参数改绑；共享的 ProjectRuntimeCache / facade 不保存可变的“当前会话”。每个问题都检查与自身相关的 A/B 项目及会话归属。

平台状态、文件定位、实际内容证据、历史来源元数据各有用途：目录事实不伪装成源码 Evidence；发现路径不等于读取内容；历史出处不直接成为当轮的新证据。不得为了单个目录或概览案例降低任意源码/测试/变更任务的取证要求。

如新增 Tool / Prompt 或响应字段，按该问题记录版本/hash与兼容策略，旧 profile 和冻结基线保留。真实模型验证前告知项目所有者。

各单项验证通过后，再用今晚完整序列及未参与调参的新问法做一次整链对照：区分开发回归与新样例，核对任务完成、实际来源、终态及成本。无需每修一个问题就跑全盘评测。

本计划不同时启动目录重构、长期 Task / Evidence / Execution Contract v2、长时记忆、MCP、多 Agent、Dense / Hybrid、Edit / Patch、执行工具或沙箱。

## 7. 每次交付的收口标准

每个问题的结果至少包括：

1. 具体根因及修复的行为。
2. 本次改动的职责边界，是否触及核心及原因。
3. 有针对性的前后对比与关联回归结果。
4. 已知限制、未解决的独立问题。
5. 下一问题及其独立范围。

当前问题验收未通过，先处理该问题，不扩大到其他能力。当前问题确实收口后交付结果，再进入下一项；标准实现不额外设置反复确认流程，封版确定的授权与范围持续有效。

## 9. R02 实施设计

根因是服务端已经选择了会话项目，但模型可调用的工具只提供检索、文件读取和变更等操作，不能查询绑定记录。此次只增加 `get_project_info` 只读工具，输入为空对象，返回当前绑定的 `project_name / root / source / available`。Handler 绑定与现有文件工具相同的服务端项目根；模型不能提交路径或项目 ID，不能查询其他项目或改绑。共享 facade 只持有不可变项目身份，不保存可变当前会话。

仅 Engineering 产品装配显式启用该工具，默认七工具及历史 Prompt 保留用于兼容和对照。Planner 新版本区分平台绑定查询与知识检索；Decision 新版本要求先查当前绑定再回答。无需新循环、预算、Evidence 类型、数据库结构或最终校验豁免。平台绑定结果不产生 `[E#]`，不代替源码、文档、测试或变更证据。Activity 只保存可用状态，不扩散绝对目录。

局部验证覆盖 Parser / Executor 拒绝路径与项目参数、中文空格目录、同名项目 A→B→A 与并发隔离、模型与历史虚假目录不能改绑、目录失效不回退、元数据无法满足源码/变更/测试取证、旧装配及 5/4/2。失效目录在消息端仍按现有策略返回 409；不为本项改写 API 可用性策略。离线通过后告知项目所有者，用少量真实 DeepSeek 请求对比 R01 与 R02。自然项目概览、绑定入口 UI、历史详情归属均在各自后续切片处理。

## 10. R03 实施设计与完成记录

R02 后再次用同原句、同六条历史复现“说一下目前的项目”：模型调用绑定查询并返回项目名和目录，终态为 completed，但没有回答项目用途与能力，也没有读取文档。R03 的验收因此以概览内容及实际来源为准，不能只以拒答减少或 completed 增加为准。

复用 `get_project_info` 与现有 Reader。工具增加 v2，可显式传布尔值 `include_documentation=true`，只检查一组有限的常用介绍入口（根 README、docs/index、docs/overview 等），返回存在且位于当前绑定项目内的安全相对路径、检查范围和是否截断；不递归扫描、不接受用户路径、不读取正文、不新增导航大工具。空结果只表示未找到这些常见入口，不宣称项目没有文档。纯绑定查询仍使用空参数及原四字段结果，v1 留作兼容与对照。
